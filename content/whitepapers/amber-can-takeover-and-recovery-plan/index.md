## ROB: history, purpose and software

ROB (R.O.B.) is Orbitus Robotics&#x27; experimental tracked humanoid: a platform for robotics education, human-robot interaction and supervised manipulation. Independent treads, a rotating torso, two seven-joint arms and grippers, cameras and range sensing connect software to a physical machine. Can-handling practice, stage demonstrations and spatial teleoperation give the project concrete tasks to investigate. [<a href="#ref-8" aria-label="Reference 8">8</a>, <a href="#ref-9" aria-label="Reference 9">9</a>, <a href="#ref-10" aria-label="Reference 10">10</a>]

The project&#x27;s archive reconstruction records ROB-specific Mac serial-control work in 2017-2018 and a surviving Cerebro Git root on January 1, 2018. Later histories add speech, perception experiments and controller arbitration. Public galleries document builds and appearances from 2019 onward. The fresh Cerebro repository of August 5, 2025 imported an existing v5 application; it was not the project&#x27;s beginning. The pre-v5 originals remain local, with provenance summarized in the supporting record. [<a href="#ref-8" aria-label="Reference 8">8</a>, <a href="#ref-10" aria-label="Reference 10">10</a>]

The public source index links six repositories and suggests starting files. The architecture separates human intent and AI-assisted planning from motor-facing ownership. This paper examines that latter boundary. It does not establish that every project feature is active together, or that the replacement controller has been physically commissioned. ## 1. Readiness is a set of separate claims

The original eight-page November 4 plan marked the candidate as ready for backup and read-only preparation. It did not mark privileged takeover, adapter reset, physical transmission or motor-stop commissioning complete. The deployed state matters as much as the source state: staged files and passing tests are not installed protection. [<a href="#ref-1" aria-label="Reference 1">1</a>]

## 2. Prove recovery before replacing ownership

The verified original-controller archive contains 48 payload files totaling 43,686,735 bytes: both host cores, 42 mapped libraries, launch files, gateway code and startup material. That archive is valuable for file restoration. It does not contain the entire boot disk, prove a bootable restore, or back up actuator EEPROM. Seven additional readable startup/recovery files were captured before the protected-policy follow-up. [<a href="#ref-1" aria-label="Reference 1">1</a>]

{{< paper-figure src="whitepapers/figures/recovery-chain.svg" alt="An original disk is imaged to verified storage, copied to independent storage, restored to a spare, and boot-tested with motor power off and CAN disconnected." caption="Figure 1. Proposed recovery chain. Image verification, an independent copy and an observed spare boot are distinct acceptance gates. None is inferred from file checksums alone." >}}

The observed boot disk was approximately 64.02 GB, with EFI, a separate boot partition and an LVM-backed root filesystem. Recovery needs the partition table, boot structures, LVM metadata and root data, with UEFI settings captured separately. The plan recommends imaging the unmounted original, restoring to an identified compatible spare, and working on that clone while preserving the original disconnected. Clonezilla documents whole-disk, LVM2 and UEFI workflows, with the imaged filesystem unmounted. [<a href="#ref-4" aria-label="Reference 4">4</a>]

A destination must be selected by verified identity and capacity, not a remembered device name. The spare must be physically compatible and large enough for the selected restore method. Boot success is still separate from correct actuator calibration or mechanical recovery.

## 3. Exclude old writers and old traffic

A single-threaded new controller does not become the only motor writer merely by starting. SocketCAN allows multiple sockets to send on the same interface. The handoff must exclude legacy processes, restart routes and direct serial access as well as constrain the replacement. Namespace lifetime also matters: physical interfaces return to the initial namespace when their network namespace is freed. The proposed ownership therefore uses a pinned, root-managed namespace with controlled driver admission. [<a href="#ref-3" aria-label="Reference 3">3</a>, <a href="#ref-5" aria-label="Reference 5">5</a>, <a href="#ref-7" aria-label="Reference 7">7</a>]

The advertised CANable2 source gave a reason to investigate adapter queues, but it was not a verified image of the flashed firmware. Closing the CAN interface cannot be treated as a proven adapter queue flush. Reset behavior, serial buffering and the age of commands reaching the wire require supported hardware evidence. [<a href="#ref-6" aria-label="Reference 6">6</a>]

ROB’s physical RIGHT mapping is CAN10/L-10; LEFT is CAN11/R-11. These labels must be checked against actual adapter and joint identity. Startup/recovery couples both arms, so a one-arm test does not by itself make a partially controlled two-arm handoff acceptable.

> A failed handoff leaves output disabled and preserves the last verified state. Crash or reconnect must not replay cached targets, automatically remove the inhibit, or revive the legacy core.

## 4. Measure stopping before continuous targets

A bounded software brake depends on the process and transport remaining able to publish. A lost process, bus or power supply may defeat that path. Before physical streaming, the project still needs measured stop latency, travel, current, mode and gravity behavior, including evidence about any drive-side timeout. A hardware shutdown switch supports supervised commissioning; it does not establish an automatic firmware watchdog.

- C0: verify physical joint IDs, signs, zeros and modes; establish measured position/rate/current limits, transport-age bounds, whole-arm sweep and stop reserve.
- M1: after an explicit operator resume, perform one reviewed, low-speed, empty-arm raise followed by measured Stop. Choose the joint and sign from fresh posture, not a synthetic test angle.
- M2: after the first motion and stop gates pass, apply a finite set of nearby mid-motion target changes through the same persistent owner. Record accepted/applied sequences and bounded tracking.
- End a run on feedback loss, unexpected current, expired targets or ownership loss. Preserve the evidence and require a fresh reviewed start rather than automatic replay.

The execution record should contain the source/package identities, arm and operator, initial measured joint state, per-joint timestamps, commanded state, current/mode, generation, accepted/applied sequence numbers, Stop outcome and each gate’s evidence reference. All original execution gates were Pending; no physical Pass is assigned in this paper.

Headless arm-only tests can be planned, but an absent head camera cannot certify the world geometry. Face pointing and VR require their own mapping and tracking-loss validation. A software-held state, quiet receive counters or stale cached telemetry does not establish physical stationarity.

> The next useful result is a measured, supported stopping experiment with a known controller and transport state. More offline check counts cannot answer that hardware question.

## 5. Rollback, reusable lessons and publication record

<div class="wp-table" role="region" aria-label="5. Rollback, reusable lessons and publication record data" tabindex="0"><table><thead><tr><th scope="col">Failure class</th><th scope="col">Recovery principle</th></tr></thead><tbody><tr><td>Only inactive staging changed</td><td>Retain the original runtime; preserve logs and identify task-owned staging precisely.</td></tr><tr><td>Handoff or feedback gate fails</td><td>Keep output disabled and ownership inhibits in place; do not retry uncertain buffered commands.</td></tr><tr><td>Return to vendor control</td><td>Support and disable arms, exclude the replacement writer, resolve queues, restore exact changed files/service state, then separately authorize motion.</td></tr><tr><td>Clone fails to boot</td><td>Use local console and the preserved original or verified image with motor power off and CAN disconnected.</td></tr><tr><td>Unexpected motion</td><td>Use the independent shutdown path, account for gravity/support, end the run and investigate.</td></tr></tbody></table></div>

The reusable lesson is that recovery and ownership should be tested before live control is expanded. A file hash proves identity, a simulated plant tests software under chosen assumptions, and a boot rehearsal tests restoration. Each answers a different question. A defensible release record carries those boundaries forward instead of collapsing them into a single “ready” label.

This edition adapts the November 4 revision-1 report and incorporates the later protected-policy backup correction recorded in the pinned handoff. The machine-readable supplement records the evidence dates and open gates. Local credentials, private backup paths, disk serials and operator conversation are excluded. The plan is a case study, not a universal robot commissioning procedure.

No new robot command, reset, installation, reboot or physical trial was performed to prepare this publication. The companion papers explain the trajectory handoff and host-boundary findings that motivated this plan.
