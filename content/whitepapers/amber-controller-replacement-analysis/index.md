## ROB: history, purpose and software

ROB (R.O.B.) is Orbitus Robotics&#x27; experimental tracked humanoid: a platform for robotics education, human-robot interaction and supervised manipulation. Independent treads, a rotating torso, two seven-joint arms and grippers, cameras and range sensing connect software to a physical machine. Can-handling practice, stage demonstrations and spatial teleoperation give the project concrete tasks to investigate. [<a href="#ref-7" aria-label="Reference 7">7</a>, <a href="#ref-8" aria-label="Reference 8">8</a>, <a href="#ref-9" aria-label="Reference 9">9</a>]

The project&#x27;s archive reconstruction records ROB-specific Mac serial-control work in 2017-2018 and a surviving Cerebro Git root on January 1, 2018. Later histories add speech, perception experiments and controller arbitration. Public galleries document builds and appearances from 2019 onward. The fresh Cerebro repository of August 5, 2025 imported an existing v5 application; it was not the project&#x27;s beginning. The pre-v5 originals remain local, with provenance summarized in the supporting record. [<a href="#ref-7" aria-label="Reference 7">7</a>, <a href="#ref-9" aria-label="Reference 9">9</a>]

This paper examines that latter boundary. It does not establish that every project feature is active together, or that the replacement controller has been physically commissioned. ## 1. Scope and audit method

The replacement question is narrower than rebuilding an entire robot: can the Ubuntu host role be replaced while retaining the motor firmware, joint references and existing transport? The original November 2 report separates that engineering route from a motor-ready release. This white paper preserves its dated findings and links later readiness evidence through the companion takeover paper.

The audit read the installed executable identity, mapped libraries, ELF dependency entries, imported symbols, launch configuration and selected disassembly. The dependency snapshot was captured at 05:42 UTC on November 3, corresponding to the November 2 local report date. Both installed arm cores matched the same archived executable hash. No binary attachment, patch, motor command or runtime configuration change was needed for these observations. [<a href="#ref-1" aria-label="Reference 1">1</a>, <a href="#ref-2" aria-label="Reference 2">2</a>]

## 2. The failure belongs at the ownership boundary

Static control flow shows a position-task handler launching a detached Ruckig worker for a new target. A worker can validate cancellation and later write the shared position array without an indivisible ownership/publication operation. Separate finite-difference samples seed velocity and acceleration. A second target can therefore introduce both inconsistent state and a stale writer. The disassembly supports this hazard; it does not prove the exact scheduling or internal values during a past physical incident. [<a href="#ref-1" aria-label="Reference 1">1</a>]

The host depends directly on trajectory math, modeling, messaging and runtime libraries. Ruckig supplies motion math. The host executable owns command ingress, threads, shared targets and output. Drake supplies model/solver facilities in other paths; direct joint command 4 bypasses that solver. The loaded Mosek and graphics branches are dependency observations, not evidence that a given arm command invoked optimization or rendering. A source filename suggesting a ROS interface likewise does not establish a ROS 2 node; the observed position handler uses LCM.

A matching-source rebuild would be attractive if the exact wrappers, generated schemas and build inputs became available. In the inspected scopes, stale objects did not establish a reproducible current build. Reusing those objects, swapping a .so, or injecting raw position messages into a still-running legacy core would leave ownership and ABI assumptions unresolved.

## 3. Reproduce the encoding; preserve uncertainty about semantics

The host position encoder emits seven three-byte frames per sample: CAN identifier 0x10 + joint number for joints 1 through 7, then opcode 0x40 and a big-endian 16-bit position word. The SI adapter converts native radians to degrees, applies the configured sign and truncates at 128 counts per degree. The observed negative-value convention adds 65,535 rather than 65,536. [<a href="#ref-3" aria-label="Reference 3">3</a>, <a href="#ref-4" aria-label="Reference 4">4</a>]

<div class="wp-table" role="region" aria-label="3. Reproduce the encoding; preserve uncertainty about semantics data" tabindex="0"><table><thead><tr><th scope="col">Compatibility example</th><th scope="col">Observed host result</th><th scope="col">Engineering consequence</th></tr></thead><tbody><tr><td>+1 degree</td><td>40 00 80</td><td>One count is 1/128 degree</td></tr><tr><td>-1 degree</td><td>40 FF 7F</td><td>Preserve the legacy negative encoding</td></tr><tr><td>Raw 0x8000</td><td>Decodes as +32768</td><td>Reject negative count -32767; it would flip sign</td></tr><tr><td>Raw 0xFFFF</td><td>Decodes as zero</td><td>Validate exact encode/decode round trips</td></tr></tbody></table></div>

The codec explicitly rejects non-finite values, invalid signs, joint-bound violations and unrepresentable signed round trips. Seven frames are assembled atomically in memory. They are not an atomic physical transaction: a real transport may accept only part of the batch. Partial or ambiguous output therefore needs a fault policy rather than an automatic retry.

For eight-byte feedback, the inspected host reads position from bytes 1-2 at 1/128 degree and current from bytes 5-6 with a divisor of 256. Velocity units, current physical units and the complete status-bit contract remain unverified. Byte 0 is retained as opaque diagnostic information; byte 7 remains raw status. Feedback IDs 0x91-0x97 correspond to the seven arm joints. Gripper and mode operations stay outside the continuous position stream.

> Protocol compatibility is evidence about the inspected host implementation. It is not independent validation of drive firmware, a motor rating, a Stop contract or permission to send these frames.

## 4. A single owner from ingress to publication

{{< paper-figure src="whitepapers/figures/controller-architecture.svg" alt="Planning and admission feed a target contract, persistent trajectory owner, exclusive transport, and unchanged actuators; measured feedback returns separately." caption="Figure 2. Proposed separation of planning, ownership and transport. Feedback is observed independently from commanded state. Physical integration and stop commissioning were open in the source report." >}}

The target contract identifies the physical arm, native-radian units, sequence, generation and a host-validated lease. A persistent owner keeps coherent commanded position/velocity/acceleration and replaces the latest pending target. Output serialization includes the Stop/ownership decision. A transport boundary accounts for per-joint receive time, publication deadlines and uncertain writes. [<a href="#ref-6" aria-label="Reference 6">6</a>]

Exclusive ownership must include every writer and every path that can restart one. A cooperative application lock or one successful SocketCAN bind does not establish exclusivity: Linux permits multiple sockets on the same CAN interface and identifiers. The proposed production handoff removes legacy writers and controls startup/recovery, CAN access and client IPC together. [<a href="#ref-5" aria-label="Reference 5">5</a>]

Physical naming is an explicit part of the contract: ROB’s RIGHT is L-10/CAN10, while LEFT is R-11/CAN11. Vendor labels are not a reliable substitute for a measured physical mapping. Firmware and stored calibration remain outside this replacement scope.

Fault containment has distinct layers. If the process can still publish, it can attempt a bounded brake from coherent commanded state. If output or feedback becomes uncertain, it latches a fault and discards old targets. If the process, bus or power is lost, an independent drive-side timeout and energy-handling strategy must be demonstrated. A software state named Held does not prove that a gravity-loaded arm is physically supported.

## 5. Recorded results and the remaining experiment

The corrected codec is pinned to commit 9e054156e0fe29cc5cfde8e785eb3a1f6e0489e2. Its replay records contain hardware_io=false and installed=false. The 42,000 frames were recorded in memory, not transmitted to the robot. The observed quantization step is not a measurement of smoothness, torque or endpoint accuracy. [<a href="#ref-4" aria-label="Reference 4">4</a>]

At this stage the project had a persistent owner and inert codec, not a commissioned replacement daemon. Later Linux, virtual-CAN and inactive-host rehearsals are described separately in the takeover paper. Counting those later checks as physical validation would blur a boundary the project deliberately retains.

- Establish fresh per-joint feedback, verified units and measured position/rate/current limits.
- Prove exclusive ownership across process, serial adapter, CAN namespace and restart paths.
- Measure adapter queue behavior, write timing, partial-batch outcomes and transport age.
- Commission supported Stop, process/bus-loss behavior and full robot/world clearance before enabling physical streaming.

> Conclusion: preserve actuator compatibility while replacing the host responsibility that is actually defective. A dependency audit tells us where components sit; source-bound replay tells us what a new component does under tested inputs. Neither replaces motor commissioning.

## 6. Reproducibility and the library ledger

The audit is pinned to bfed885d51f36fb6f529fe68043e48f1f9b6cb4d, and codec results to 9e054156e0fe29cc5cfde8e785eb3a1f6e0489e2. Reproduction starts with the recorded identity and dependency data, then the isolated ContinuousArm build described in the source README. The public supplements contain all 42 mapped-library identities and curated test metrics. Hashes make revisions comparable; they do not certify behavior.

The ledger labels a library Direct when its SONAME appears in the core’s DT_NEEDED list. Other mapped objects are labeled Mapped/transitive; this category includes the dynamic loader. It does not assert that every object has the same calling path or that an imported symbol executed. Full dependency edges remain available in the pinned project record.

This white paper adapts the fourteen-page November 2 engineering report. It excludes operator conversation, credentials, host paths and proprietary binary payloads. The original observed byte behavior is documented as an interoperability finding, with unresolved physical semantics called out rather than guessed.
