## 1. Executive direction and evidence boundary

> The suite is a developing investigation workbench. Its strongest opportunity is a traceable path from a discovered device or suspicious flow to the local process, publisher and evidence that justify an analyst decision.

SignalAtlas combines wireless observations, bounded native LAN discovery, imported network evidence and a graphical TShark workflow. BlackViper contributes Endpoint Security events, execution-policy controls, a separate Network Extension and integrations with established file and dependency scanners. These components are useful together, but their presence does not establish full Nmap, Wireshark, Jamf or enterprise endpoint detection and response (EDR) equivalence. [<a href="#ref-1" aria-label="Reference 1">1</a>]

This edition freezes the inspected implementation at SignalAtlas commit 30a867890f6e and BlackViper commit 4314a0d82219. It draws on their checked-in documentation and validation records. Implementation means code exists at that baseline; recorded validation means a specific test is documented; live acceptance means the actual permissioned workflow has been exercised. Publication of this paper is separate from product distribution. The public supplement identifies source paths relative to each project, complete commit IDs and evidence hashes. ## 5. Apple Endpoint Security: two execution paths

{{< paper-figure src="whitepapers/figures/security-two-path-architecture.svg" alt="An authorization event follows local policy directly to an OS response. A separate bounded queue feeds evidence storage and ML/LLM investigation." caption="Figure 1. Proposed separation of time-critical authorization and asynchronous analysis. Existing framework integrations supply inputs; the complete analysis plane is future work." >}}

Apple Endpoint Security is a C API for observing system events and authorizing supported pending operations. A client receives notifications and authorization requests; it can be packaged in a system extension installed through the host app. This is the framework intended by the phrase low-level security endpoint framework. It is distinct from Linux eBPF and from macOS BPF packet devices. [<a href="#ref-2" aria-label="Reference 2">2</a>]

An authorization message carries a deadline. Missing it can terminate or restart a client, and repeated misses can prevent new client connections. The proposed callback uses reviewed local rules and prepared state, with a documented fallback. It never waits for an LLM, cloud service, DNS lookup or analyst. Cache use and invalidation must match each event API and policy revision. [<a href="#ref-3" aria-label="Reference 3">3</a>]

Copy or retain messages using supported APIs before processing beyond their documented lifetime; keep queues bounded and release retained resources. Record sequence gaps, queue losses, subscription changes and restarts as coverage evidence. Absence of a suspicious event during a gap is not evidence of safety. Apple exposes per-type sequence numbers for detecting kernel drops. [<a href="#ref-4" aria-label="Reference 4">4</a>, <a href="#ref-5" aria-label="Reference 5">5</a>]

Client entitlement and TCC/Full Disk Access are separate deployment requirements. Network Extension supplies a separate flow/filter path; dumpcap uses packet-capture access. ChmodBPF is Wireshark&#x27;s supported macOS capture-permission mechanism, with administrative installation. The app should not collect an administrator password itself. Granting packet access does not grant Endpoint Security authorization rights. [<a href="#ref-5" aria-label="Reference 5">5</a>, <a href="#ref-6" aria-label="Reference 6">6</a>, <a href="#ref-9" aria-label="Reference 9">9</a>]

## 6. Automatic correlation with explicit uncertainty

{{< paper-figure src="whitepapers/figures/security-correlation-graph.svg" alt="Process instance, connection and packet evidence are linked with direct evidence. Asset and service interpretations are separately marked as inferred relationships." caption="Figure 2. Proposed relationship types. A shared address is an observation, not sufficient proof of device identity or causality." >}}

Use an append-only observation model: case and sensor IDs, source kind/version, capture or import settings, record locator, source hash, event and ingest times, clock basis and quality flags. Store derived links separately with join method, candidate count, time tolerance and the exact supporting observations. A hash detects changed bytes; it does not authenticate the original source by itself.

For a local flow-to-process join, require a compatible observation domain and protocol, both endpoint addresses and ports, temporal overlap within a justified clock tolerance, and a process-instance identity. Viper already records connection/application fields useful for this work. A PID alone is reusable; pair it with a boot/session and audit-token or process-start identity where available. Preserve actual process and responsible application as separate identities. [<a href="#ref-1" aria-label="Reference 1">1</a>]

Maintain competing candidates when DHCP reuse, NAT, VPN translation, proxies, reused ports or uncertain clocks make a join ambiguous. Do not invent a confidence percentage: use direct, inferred, ambiguous and unknown states until calibrated probabilities exist. Remote packets do not identify the remote process without remote endpoint telemetry. MAC randomization and BLE identifiers further limit device fusion.

> Example, not an observed incident: a persistence write, a new executable instance and an outbound flow share a defensible local identity/time chain. The interface can show all three records and packet references. If VPN translation breaks the tuple match, it should show an unresolved link rather than attribute the flow to that process.

A correlation service must read the retained records, not only the UI&#x27;s packet/flow summary. It must also carry the acquisition scope into every case so filters, truncation, missing packets and time bounds remain visible. At the assessed baseline, shared report provenance does not yet carry every live-acquisition setting. [<a href="#ref-1" aria-label="Reference 1">1</a>]

## 7. Full evidence retention and useful data categories

The baseline preserves available decoded values and source bytes within explicit limits. Authentication values, cookies, query data and payload fields are categorized rather than omitted. Network access remains enabled for the analysis worker; optional name resolution is a recorded setting. A model can consume selected features without altering the underlying evidence. This is a distinction between storage and analysis inputs, not a redaction policy. [<a href="#ref-1" aria-label="Reference 1">1</a>]

Current private log directories and files use restrictive filesystem modes. The proposed evidence service adds explicit retention/capacity policy, protected indexing, access audit and export provenance. The existing capture worker is bounded: decoded output is capped, report/record counts are limited, and the displayed summary is smaller than the retained record set. Exceeding a limit must create an incomplete or failed status, never a false all-clear. [<a href="#ref-1" aria-label="Reference 1">1</a>]

Capture filters select what is acquired; display filters select what is analyzed or displayed. Neither decrypts encrypted payloads. A normal host interface does not necessarily observe other devices&#x27; unicast traffic on a switched network. Enterprise network visibility requires appropriate sensor placement, which is a deployment design separate from adding an app control. [<a href="#ref-7" aria-label="Reference 7">7</a>, <a href="#ref-8" aria-label="Reference 8">8</a>]

> Complete retention means preserving what the configured sensor actually acquired, with limits and gaps recorded. It cannot mean every byte on every network or plaintext hidden by encryption.

The proposed learning ladder starts with transparent rates, counts and temporal rules, then compares tabular and small sequence models. Only afterward should self-supervised graph embeddings or traffic representations compete for promotion. ## 9. LLM investigation with verifiable evidence

The proposed LLM role is evidence navigation and explanation: summarize a timeline, identify contradictory observations, explain an imported finding, suggest a bounded query, or draft a policy proposal for review. Retrieval-augmented generation (RAG) should retrieve typed observations and approved reference material with stable record IDs. It must not treat plausible text as a substitute for a missing record.

Karanjai and colleagues demonstrate passive prompt injection through attacker-controlled network-log fields. Their LogInject evaluation shows that stored telemetry can contaminate a later analyst query. This directly applies to protocol strings, filenames, URLs and payloads entering an assistant context. Formatting data as JSON or asking the model to ignore instructions is not a complete defense. [<a href="#ref-24" aria-label="Reference 24">24</a>]

The proposed controls are architectural: separate trusted instructions from evidence, avoid unrestricted shell tools, constrain retrieval to the case, validate generated arguments, and prevent retrieved content from changing destinations or privileges. Keep all captured values in the evidence store; prepare a typed model input appropriate to the task. If a model needs raw content, preserve its provenance and test the surrounding action boundary against hostile content.

Record model identity, prompt/template version, retrieval set and output. An investigation should remain reproducible when a model is upgraded or unavailable. External enrichment and remote model services remain optional deployment choices with explicit destinations and data handling; their latency or outage must never hold up an OS authorization reply.

> Acceptance requires grounded claims, useful uncertainty and bounded actions. An eloquent explanation that assigns a remote flow to the wrong local process is a failure even when its final threat label happens to be correct.

## 10. Evaluation before promotion to protection

No new detection effectiveness experiment was performed for this paper. The following is a proposed acceptance program. Thresholds must be chosen before testing for a defined pilot workload; no unmeasured percentage is presented as a product result.

<div class="wp-table" role="region" aria-label="10. Evaluation before promotion to protection data" tabindex="0"><table><thead><tr><th scope="col">Evaluation layer</th><th scope="col">Measure and test</th><th scope="col">Promotion gate</th></tr></thead><tbody><tr><td>Evidence integrity</td><td>Hash and record round trips; repeated fields; capture failure; partial output; schema migration.</td><td>Every displayed claim resolves to source records; limits and incomplete sessions are visible.</td></tr><tr><td>Correlation</td><td>Known local flows with PID/port reuse, clock skew, DHCP, VPN, NAT and multiple candidates.</td><td>Measure precision, coverage and abstention separately. No forced identity on deliberately ambiguous fixtures.</td></tr><tr><td>Behavior models</td><td>Temporal and host/site holdouts; benign administration, builds, updates and validated attack simulations.</td><td>Compare against rules and simple models with confidence intervals and identical inputs.</td></tr><tr><td>Analyst utility</td><td>False leads per endpoint/day, time to inspect, duplicate alerts, useful incident recall and review agreement.</td><td>Show an improvement in the intended workflow without hiding alert volume behind aggregate accuracy.</td></tr><tr><td>LLM grounding</td><td>Unsupported claims, wrong source IDs, missed contradictions, prompt injection and action-boundary attempts.</td><td>Report both outcome and evidence quality; no unauthorized action in the defined adversarial test set.</td></tr><tr><td>Runtime reliability</td><td>Callback deadline misses, sequence gaps, local queue loss, p95/p99 processing latency, memory and energy.</td><td>Sustain the pilot workload with documented overload behavior. Model failure leaves local policy available.</td></tr><tr><td>Deployment</td><td>Entitlements, signing/notarization, permissions, boot/login behavior, upgrades and rollback.</td><td>A clean-machine, permissioned live workflow succeeds; source builds alone are insufficient.</td></tr></tbody></table></div>

Prevent leakage by splitting before feature construction and learning vocabularies only on training data. Keep duplicate incidents, related captures and process lineages in one partition. Evaluate rare attacks with precision/recall and precision-recall curves, including false-alert burden; overall accuracy is misleading under strong class imbalance. Calibrate any probability estimate and measure drift after OS, workload or network changes.

Use reviewed labels that distinguish confirmed incident, benign activity, unknown and insufficient visibility. Analyst feedback is useful but noisy; it should enter a versioned review process rather than silently retrain production protection. New detectors should first run in shadow mode, followed by a bounded pilot and a rollback-ready release.

Learned prioritization</td><td>Versioned feature extraction and simple baseline models, then selected graph/traffic candidates.</td><td>Held-out improvement over the baseline with calibration, drift and resource measurements.</td></tr><tr><td>6. Milestones describe deliverables and gates, not promised dates. Several can progress independently, but learned models depend on reliable evidence and labels, and trustworthy explanations depend on reliable correlation. Fleet deployment and enterprise operations remain separate product work even if an individual Mac workflow succeeds.

Retain dedicated tools where they are strongest: Nmap for active assessment, Wireshark/TShark for protocol interpretation, Suricata for network detections, and fleet platforms for management and centralized operation. The suite should preserve their attribution and original findings while making cross-tool investigation easier. Integrating an engine does not make its findings a proprietary detector.

> The defensible next generation is an evidence system with useful machine intelligence: fast local policy, durable observations, explainable relationships, measured learned ranking and analyst-controlled decisions. The immediate engineering priority is the correlation foundation that makes every later model answer checkable.
