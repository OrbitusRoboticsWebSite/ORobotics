## 1. ROB and the purpose of the spare

ROB is Orbitus Robotics&#x27; experimental tracked humanoid for robotics education, human-robot interaction and supervised manipulation. Its two seven-joint arms share a moving torso and mobile base. Cerebro coordinates perception and command admission; phone and visionOS interfaces provide operator input. A second arm-control computer could support recovery, development and a later replacement controller, provided its software, transport and timing are qualified. [<a href="#ref-6" aria-label="Reference 6">6</a>, <a href="#ref-7" aria-label="Reference 7">7</a>, <a href="#ref-8" aria-label="Reference 8">8</a>]

This study asks whether an older AMBER B1 computer can become a reproducible two-arm host. A November 5, 2026 read-only audit compared its installed stack with the working dual-arm master. The contribution is a measured compatibility assessment and a staged conversion plan. It is not a completed clone, an X-Hub firmware identification or a physical control trial. [<a href="#ref-1" aria-label="Reference 1">1</a>]

## 2. What is installed, and what remains unknown

{{< paper-figure src="whitepapers/figures/xhub-installed-stack.svg" alt="Installed path: Robot Studio to the ROS 2 Foxy controller, then SOEM EtherCAT to an X-Hub endpoint. The link was disconnected during the audit." caption="Figure 1. Installed single-arm architecture inferred from launch files and binary inspection; no active X-Hub exchange was performed." >}}

The installation belongs to the B1 V1 X-Hub/EtherCAT software family. Its launch scripts select amber_b1_hw_gui_ethercat.launch.py with hardware and EtherCAT enabled. The AmberB1Hardware plugin imports SOEM functions and uses a fixed network interface. The web/API configuration reports version 1.1; this value does not identify the circuit board or hub firmware. [<a href="#ref-1" aria-label="Reference 1">1</a>, <a href="#ref-2" aria-label="Reference 2">2</a>]

The EtherCAT-facing port had no carrier, matching the reported disconnected cables. The driver, GUI control node and command backend were inactive. The historical log records one slave, 92 input bytes, 56 output bytes and expected working counter 3; later entries report packet errors and a lost slave. These describe a past session, not a diagnosis of the powered but disconnected hubs. [<a href="#ref-1" aria-label="Reference 1">1</a>]

The pinned public vendor tree exposes no C/C++ source tree; archived release contents were not exhaustively searched. Installed headers contain CAN error counters, per-joint CAN status and message proxy fields. This supports investigating a CAN bridge, but proves neither electrical compatibility nor interchangeable motor commands. [<a href="#ref-1" aria-label="Reference 1">1</a>, <a href="#ref-2" aria-label="Reference 2">2</a>]

## 3. Why a direct copy is insufficient

<div class="wp-table" role="region" aria-label="3. Why a direct copy is insufficient data" tabindex="0"><table><thead><tr><th scope="col">Observed item</th><th scope="col">Older host</th><th scope="col">Current dual-arm master</th></tr></thead><tbody><tr><td>Processor</td><td>Celeron N2840; 2 cores</td><td>Celeron J4125; 4 cores</td></tr><tr><td>Memory / swap</td><td>1.96 GB RAM; no swap</td><td>3.92 GB RAM; 3.99 GB swap</td></tr><tr><td>Disk capacity</td><td>32,017,047,552 bytes</td><td>64,023,257,088 bytes</td></tr><tr><td>Boot layout</td><td>UEFI; DOS/MBR; EFI + ext4</td><td>UEFI; GPT; EFI + boot + LVM</td></tr><tr><td>OS / C runtime</td><td>Ubuntu 20.04.3 / glibc 2.31</td><td>Ubuntu 22.04.3 / glibc 2.35</td></tr><tr><td>Installed transport</td><td>Single-arm SOEM EtherCAT</td><td>Two USB-CAN adapters</td></tr></tbody></table></div>

A raw image of the current master cannot fit the smaller disk unchanged. The preservation-first path is separate replacement media, with exact capacity and connector compatibility verified before a restore. A compact fresh installation is another option; neither requires overwriting the original V1 system. [<a href="#ref-1" aria-label="Reference 1">1</a>]

Both current arm executables require GLIBC_2.34, which the old glibc 2.31 installation cannot provide. Ubuntu 22.04 is the initial compatibility baseline, with all other libraries, ABI and CPU instruction requirements still subject to verification. Foxy targets Ubuntu 20.04; its installed binaries should not be casually mixed into another ROS distribution. Canonical lists standard maintenance for Ubuntu 22.04 through May 2027, so a supported successor is a separate validation task. [<a href="#ref-1" aria-label="Reference 1">1</a>, <a href="#ref-3" aria-label="Reference 3">3</a>, <a href="#ref-4" aria-label="Reference 4">4</a>]

A 2.025-second sample of the current master measured 194.1% and 187.1% CPU for the two vendor processes, with 19 threads each: about 3.81 logical CPUs combined. Percentages use one fully occupied logical CPU as 100%. This short snapshot is not a benchmark on the N2840 or a worst-case timing study. It warns against copying the workload unchanged; it does not show that an efficient two-arm controller cannot run on two cores. [<a href="#ref-1" aria-label="Reference 1">1</a>]

The older launchers also assume one arm: broad process matching during restart, shared controller names, unprefixed joints, a fixed command endpoint and a fixed interface. Starting the same launcher twice does not establish isolated two-arm ownership. [<a href="#ref-1" aria-label="Reference 1">1</a>, <a href="#ref-2" aria-label="Reference 2">2</a>]

## 4. Models, transport and continuous retargeting

<div class="wp-table" role="region" aria-label="4. Models, transport and continuous retargeting data" tabindex="0"><table><thead><tr><th scope="col">Model inspected</th><th scope="col">Recorded values</th><th scope="col">Implication</th></tr></thead><tbody><tr><td>Old standalone URDF</td><td>J7: -314 to +314 rad; all joint velocities: 10.</td><td>Not a measured limit profile.</td></tr><tr><td>Old launched Xacro</td><td>J7: +/-3.05 rad; J1-4 velocities: 3.1415; J5-7: 5.23.</td><td>Geometry and origins also differ from the standalone model.</td></tr><tr><td>Current solver files</td><td>One 7-joint chain per arm; limits +/-2.09; effort 100000; velocity 1000000.</td><td>Large values cannot be treated as commissioned actuator ratings.</td></tr></tbody></table></div>

Joint axes, signs, zero offsets, geometry and limits must be reconciled against the identified arm revision and fresh feedback. The selected solver models do not describe the entire mobile body, torso, open grippers, payload and observed table/floor. Collision planning must include these frames and swept paths, especially when the base approaches a table. Model edits alone cannot serialize overlapping commands. [<a href="#ref-1" aria-label="Reference 1">1</a>, <a href="#ref-5" aria-label="Reference 5">5</a>]

Two transport paths remain candidates. Direct, isolated USB-CAN would resemble the current master, but requires verified pinout, power separation, termination, bitrate, motor IDs, units, modes and watchdogs. Retaining the two X-Hubs requires a tested multi-slave EtherCAT topology or supported separate interface paths. With one of the older host&#x27;s two NICs used for LAN, interface allocation matters. Neither a conventional switch nor a second copy of the single-arm driver establishes the needed topology. [<a href="#ref-1" aria-label="Reference 1">1</a>]

{{< paper-figure src="whitepapers/figures/xhub-dual-owner.svg" alt="Cerebro and VR targets pass shared scene, limit and Stop admission, then branch into independent persistent right and left arm owners with exclusive transport writers." caption="Figure 2. Proposed two-arm ownership boundary. The transport and physical stop behavior still require commissioning." >}}

Each arm should have one persistent trajectory owner and a bounded latest-target mailbox. A new goal updates a coherent position, velocity and acceleration state while limits and Stop remain under the same owner. VR input adds relative clutching, timestamp checks, quaternion interpolation, continuous-branch inverse kinematics and tracking-loss behavior. These are proposed integration requirements. The old GUI was not shown to contain the same detached-command-worker defect documented for the newer core. [<a href="#ref-1" aria-label="Reference 1">1</a>, <a href="#ref-5" aria-label="Reference 5">5</a>]

## 5. A conversion sequence with reversible gates

<div class="wp-table" role="region" aria-label="5. A conversion sequence with reversible gates data" tabindex="0"><table><thead><tr><th scope="col">Stage</th><th scope="col">Work and completion evidence</th></tr></thead><tbody><tr><td>1. Preserve originals</td><td>Keep the V1 disk intact. Create coordinated offline images, independent copies and a verified restore target. File hashes alone do not demonstrate a bootable recovery.</td></tr><tr><td>2. Prepare separate media</td><td>Use a compatible SSD or compact clean installation. Assign a unique machine identity and independent credentials. Disable motor startup before first boot with motor links disconnected.</td></tr><tr><td>3. Reproduce the runtime</td><td>Verify libraries, ABI and instruction requirements. Separate per-arm models and profiles from host configuration. Install and test deliberate startup/recovery ownership inhibition.</td></tr><tr><td>4. Qualify this CPU offline</td><td>Exercise both inert owners and simulated transports under realistic load. Record timing, queue age, RAM, temperature and faults; investigate busy polling. Use a stronger host if margin is inadequate.</td></tr><tr><td>5. Resolve the transport</td><td>Identify both hubs and arm revisions. Verify topology, electrical interfaces, feedback codec, PDO layout where applicable, signs, zeros, modes and drive-side watchdog behavior.</td></tr><tr><td>6. Commission incrementally</td><td>Under separate physical-test authorization: one arm, tiny bounded move and Stop, then moving retargets; repeat for the other arm, then paired motion and VR.</td></tr></tbody></table></div>

> First implementation milestone: a bootable development clone with a unique identity, motor startup disabled, two independent simulated arm owners and a reproducible deployment manifest. This milestone does not require a motor adapter change.

Physical-side routing must be explicit. The current installation&#x27;s internal L/R names are reversed relative to physical sides, so a clone must bind verified adapter identities and profiles to the intended arm rather than infer side from directory names or enumeration order. New hardware needs its own mapping. [<a href="#ref-1" aria-label="Reference 1">1</a>]

The source-owned controller candidate remains physically inert in the cited commissioning record. Prior software and virtual-CAN tests support continued development; they do not implement or authorize live streaming on either of the proposed transports. [<a href="#ref-6" aria-label="Reference 6">6</a>]

## 6. Acceptance criteria and limits of the evidence

<div class="wp-table" role="region" aria-label="6. Acceptance criteria and limits of the evidence data" tabindex="0"><table><thead><tr><th scope="col">Gate</th><th scope="col">Required evidence before promotion</th></tr></thead><tbody><tr><td>Restore and routing</td><td>Boot the spare with motor links detached; verify rollback, unique per-arm endpoints and rejection of missing or swapped adapters.</td></tr><tr><td>Exclusive ownership</td><td>A second writer cannot acquire the arm. Legacy startup and recovery cannot silently restore a competing controller.</td></tr><tr><td>Retarget continuity</td><td>Forward/reverse goals and input floods preserve bounded position, velocity, acceleration and jerk, stable worker count and latest-target replacement.</td></tr><tr><td>Feedback and Stop</td><td>Stale feedback, packet loss, partial writes, queue backlog, disconnect and restart produce defined fault behavior without automatic resumption.</td></tr><tr><td>Timing at 200 Hz</td><td>A 5 ms period sets the scheduling budget. Measure worst-case and high-percentile latency, misses and queue age under load; declare release thresholds before testing.</td></tr><tr><td>World and VR</td><td>Validate measured model transforms and full swept paths. Exercise clutch release, tracking loss, stale timestamps, orientation equivalence and IK branch changes.</td></tr></tbody></table></div>

The audit preserved 393 regular files in a 15,203,162-byte archive and compared every archived file SHA-256 with fresh source reads, with zero mismatches. This establishes selected-file integrity at the sampled times. It is not a whole-system backup, a reproducible vendor build or a tested disk restore. The archive and private report are not redistributed; the supplement provides curated findings and identity hashes. [<a href="#ref-1" aria-label="Reference 1">1</a>]

No X-Hub firmware, EEPROM identity or physical board label was obtained. No electrical compatibility, two-hub topology, motor tracking, real-time deadline margin, whole-disk recovery or physical stop behavior was validated. SMART tooling was absent, and physical power stability was not tested. These are open work items, not negative test results. [<a href="#ref-1" aria-label="Reference 1">1</a>]

> Conclusion: use the old computer first as a preserved development and recovery candidate. A dual-arm conversion becomes credible when media recovery, runtime compatibility, timing, transport semantics and exclusive motion ownership each have their own evidence. The plan does not require an arm to settle before every future goal; it requires a commissioned controller that can retarget continuously.
